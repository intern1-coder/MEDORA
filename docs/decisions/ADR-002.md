# ADR-002: Argon2id Password Hashing Strategy and Security Lifecycle

## Status
- **Algorithm Selection**: **OWNER APPROVED** (Argon2id).
- **Runtime Implementation**: **NOT IMPLEMENTED** (No code written yet).
- **Configuration Parameters & Reset Policies**: **PROPOSED** (Awaiting final parameter review).

## Context
Medora requires a cryptographically resilient password hashing scheme to protect credentials for patients, doctors, administrative staff, and system administrators. Traditional algorithms like MD5 or SHA-256 (even salted) are vulnerable to GPU acceleration attacks. Argon2id combines memory-hard resistance against GPU brute-force and side-channel resistance.

The project owner has explicitly approved the **Argon2id** algorithm.

---

## Technical Design & Proposed Configuration

### 1. Proposed Parameters (Engineering Recommendation)
In accordance with OWASP Password Storage guidelines:
- **Variant**: `argon2id` (v=19).
- **Memory Cost (`m`)**: 64 MB (65,536 KiB) per hash.
- **Time Cost / Iterations (`t`)**: 3 passes.
- **Parallelism (`p`)**: 1 thread.
- **Hash Length**: 32 bytes (256 bits).
- **Salt Generation**: 16 bytes (128 bits) of cryptographically secure random bytes generated via CSPRNG (`crypto.randomBytes`).

### 2. Salt and Hash Storage Format
Argon2id modular crypt format string:
`$argon2id$v=19$m=65536,t=3,p=1$<salt-b64>$<hash-b64>`
This standard format embeds the algorithm version, parameters, salt, and resulting hash in a single string, facilitating self-contained verification.

### 3. Password Verification & Future Hash Upgrades
- Verification utilizes `argon2.verify(hashedPassword, plainPassword)`.
- Re-hashing check: On successful authentication, the system evaluates `argon2.needsRehash(hashedPassword, currentOptions)`. If system cost parameters are increased in future releases, the hash is automatically recalculated and updated in PostgreSQL transparently.

### 4. Credential Handling
- Inbound passwords are typed via Zod schemas and explicitly stripped/omitted from any logging middleware, error stacks, or audit payloads.
- Passwords in memory are treated as transient and garbage-collected immediately following hash verification.

### 5. Password Reset and Account Recovery [PROPOSED]
- Password resets use time-limited (15-minute), single-use cryptographically random tokens stored as SHA-256 hashes in the database.
- Initiating a password reset or successfully changing a password immediately revokes all active refresh tokens associated with that user account across all devices.

## Consequences & Trade-offs
- Modern, memory-hard cryptographic protection.
- Higher server RAM/CPU cost during authentication spikes; rate-limiting on login and registration endpoints (`express-rate-limit`) is essential to prevent CPU exhaustion.
