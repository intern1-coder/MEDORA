# ADR-003: Browser-Based PDF Generation Engine Evaluation and Deployment Architecture

## Status
- **Browser-Based PDF Generation Principle**: **OWNER APPROVED** (HTML templates rendered through a browser engine).
- **Runtime Implementation**: **NOT IMPLEMENTED** (No packages installed or code written yet).
- **Engine (Puppeteer-Core) & Template Tool (Handlebars)**: **PROPOSED** (Engineering recommendation).
- **Container Deployment Model (Embedded vs Sidecar)**: **UNRESOLVED / PROPOSED** (Evaluation presented below).

## Context
Medora requires automated generation of clinical and administrative documents, specifically:
1. Patient Consultation Summaries
2. Digital Prescriptions
3. Doctor-Approved Diet Plans
4. Itemized Invoices and Payment Receipts

Clinical reports require precise typographic styling, pagination controls, hospital branding, barcodes/QR codes, and tamper-evident watermarks. The project owner has approved browser-based rendering of HTML/CSS templates.

---

## 1. Engine Evaluation: Playwright vs Puppeteer

| Evaluation Criteria | Puppeteer (GoogleChrome) | Playwright (Microsoft) |
| :--- | :--- | :--- |
| **Primary Focus** | Chrome/Chromium automation | Multi-browser automation (Chromium, Firefox, WebKit) |
| **PDF Generation API** | `page.pdf({ format: 'A4', printBackground: true, margin: ... })` | `page.pdf({ format: 'A4', printBackground: true, margin: ... })` |
| **Binary Footprint** | Lightweight Chromium download via `puppeteer` or uses system Chromium via `puppeteer-core` | Full test framework download, though `playwright-core` can isolate Chromium |
| **Container & Docker Size** | Compact Alpine/Debian slim base image; well-documented Alpine setup | Heavier container image due to multi-platform dependencies |
| **Node.js Integration** | Direct, mature, minimal overhead for single-purpose PDF tasks | Excellent, but designed primarily as an end-to-end testing orchestrator |
| **Memory Consumption** | ~50–80 MB per browser page instance | ~70–100 MB per browser context |
| **HTML Injection Protection** | Template engine dependent (Handlebars with strict auto-escaping) | Template engine dependent (Handlebars with strict auto-escaping) |

---

## 2. Deployment Architecture Comparison: Embedded vs Sidecar [UNRESOLVED / PROPOSED]

| Comparison Dimension | Option A: Embedded Chromium in Backend Container | Option B: Dedicated PDF Rendering Microservice (Sidecar) |
| :--- | :--- | :--- |
| **Architecture** | Headless Chromium runs directly within the Node.js Express application container via `puppeteer-core`. | Dedicated lightweight Node.js/Chromium container listening on an internal HTTP endpoint exclusively for rendering HTML to PDF. |
| **Development Complexity** | **Low**. Single container; simple `docker-compose.yml` for local development. | **Medium**. Requires managing two container builds, internal service discovery, and shared network. |
| **Resource Isolation** | **Shared**. Heavy PDF rendering spikes consume memory and CPU from the Express API process. | **Isolated**. Browser memory spikes cannot starve the core API server or degrade patient check-in response times. |
| **Image Size** | Backend image increases by ~250 MB due to Chromium and system font libraries. | Backend image remains lean; only the PDF sidecar image carries Chromium libraries. |
| **Network Latency** | Zero network overhead (in-memory IPC). | Small HTTP transfer latency transmitting rendered HTML and binary PDF buffers over internal network. |
| **Scaling Characteristics** | Scales jointly with backend API instances. | Scales independently based on report generation demand. |

### Engineering Recommendation
- **Phase 3 & Initial Development**: Adopt **Option A (Embedded Chromium)** to minimize development and testing complexity.
- **Production Scaling**: If document generation load creates API performance contention, transition to **Option B (Dedicated Sidecar)** without changing template or business logic.

---

## 3. Template Architecture & Security Hardening [PROPOSED]
- **Engine**: **Handlebars** (`handlebars`) with strict auto-escaping enabled (`{{variable}}`). Raw unescaped strings (`{{{raw}}}`) are strictly prohibited.
- **SSRF Defense**: Chromium launches with sandboxing flags and navigation locked to `about:blank`. Outbound network requests inside the page are intercepted and aborted (`page.setRequestInterception(true)`).
- **Access Permissions**: PDFs are generated dynamically on authenticated endpoints. Receptionists are strictly forbidden from downloading clinical summaries or prescriptions.

## Consequences & Trade-offs
- Delivers pixel-perfect clinical layouts, standard headers, and reliable multi-page printing.
- Evaluates container deployment trade-offs objectively for project owner determination.
